=> Complete Lifecycle of a Java Program

    -> Step 1: Write Source Code

        -> We write the Java source code in MyApplication.java.

    -> Step 2: Compilation

        -> The Java Compiler (javac) compiles MyApplication.java.
        -> The compiler checks the source code for compile-time errors.
        -> If compilation is successful, MyApplication.class is generated.
        -> The .class file contains platform-independent Bytecode.

    -> Step 3: Start the JVM

        -> We execute the program using the java command.
        -> The JVM starts and begins processing the required classes.

    -> Step 4: Loading

        -> The Class Loader Subsystem loads the required .class files.

        -> Java mainly uses three ClassLoaders:

            -> Bootstrap ClassLoader
                -> Parent of the other ClassLoaders.
                -> Loads core Java classes required by the JVM.

            -> Platform ClassLoader
                -> Loads platform-level Java classes and libraries.

            -> Application ClassLoader
                -> Loads application/user-defined classes from the classpath.

        -> Parent Delegation Model:

            Application ClassLoader
                    |
                    v
            Platform ClassLoader
                    |
                    v
            Bootstrap ClassLoader

        -> The request is delegated to the parent first.
        -> If the parent cannot load the class, the child ClassLoader gets a chance to load it.

        -> Since MyApplication is our user-defined class,
           it is normally loaded by the Application ClassLoader.

    -> Step 5: Linking

        -> After loading, JVM performs Linking.

        -> Linking contains three phases:

            1. Verification

                -> JVM verifies that the Bytecode is valid and safe.
                -> It checks whether the .class file follows JVM rules.

            2. Preparation

                -> Memory for static fields is prepared.
                -> Static fields initially receive their default values.

                Example:

                    static int count = 10;

                During Preparation:

                    count = 0

            3. Resolution

                -> Symbolic references used in the Bytecode are resolved
                   into actual runtime references when required.

    -> Step 6: Initialization

        -> JVM initializes the class.

        -> Static fields receive their explicitly assigned values.

        Example:

            static int count = 10;

        During Preparation:

            count = 0

        During Initialization:

            count = 10

        -> Static initialization blocks are also executed.
        -> Static field initializers and static blocks execute
           according to their source-code order.

    -> Step 7: Execution

        -> After the required class initialization, JVM invokes main().

        -> main() becomes the entry point of our application.

        -> JVM starts executing the instructions inside main().

        -> If an object is created using:

            Employee e1 = new Employee();

           then:

            -> A new Employee object is allocated in Heap Memory.
            -> Its instance fields first receive their default values.
            -> The constructor executes.
            -> The reference returned by new Employee() is assigned to e1.
            -> If e1 is a local variable, that reference is stored
               in the current method's Stack Frame.

    -> Step 8: First Output

        -> When JVM reaches a statement such as:

            System.out.println("Hello");

        -> The statement executes and the first output is displayed.

=> What is Bytecode?
    -> Bytecode is the intermediate code generated by the Java Compiler (`javac`).
    -> It is stored inside the `.class` file.
    -> It is platform-independent.
    -> It cannot be executed directly by the CPU.
    -> JVM executes the Bytecode using:
        -> Interpreter
        -> JIT (Just-In-Time) Compiler

=> Who converts `.java` into `.class`?
    -> The Java Compiler (`javac`) converts `.java` into `.class`.
    -> During compilation:
        -> Checks syntax errors.
        -> Generates Bytecode.
    -> Example:
        -> MyApplication.java
        -> javac
        -> MyApplication.class

=> What is the role of the JVM after the `.class` file is created?
    -> Starts the JVM.
    -> Loads the required classes.
    -> Verifies the Bytecode.
    -> Performs Linking.
        -> Verification
        -> Preparation
        -> Resolution
    -> Performs Initialization.
    -> Invokes the `main()` method.
    -> Executes Bytecode using:
        -> Interpreter
        -> JIT Compiler
    -> Produces the final output.

=> What is Class Loading?
    -> Class Loading is the process of loading a `.class` file into JVM memory before execution.
    -> It is performed by the Class Loader Subsystem.
    -> It loads only `.class` files.
        -> Never `.java` files.
    -> Responsibilities:
        -> Locate the class.
        -> Load the class into JVM memory.
        -> Make it available for execution.

=> What are the three types of Class Loaders?
    -> Bootstrap ClassLoader
    -> Platform ClassLoader
    -> Application (System) ClassLoader

=> What is the responsibility of Bootstrap ClassLoader?
    -> Loads Core Java classes.
    -> Loads Java Runtime classes.
    -> Examples:
        -> java.lang.String
        -> java.lang.Object
        -> java.lang.System
        -> java.util.ArrayList
        -> java.util.HashMap
    -> It is the parent of all Class Loaders.

=> What is the responsibility of Platform ClassLoader?
    -> Loads JDK platform libraries.
    -> Loads classes that are not part of the core Java libraries but are provided by the JDK.
    -> Examples:
        -> java.sql.*
        -> java.xml.*
        -> javax.naming.*

=> What is the responsibility of Application (System) ClassLoader?
    -> Loads user-defined classes.
    -> Loads classes available in the application's classpath.
    -> Examples:
        -> MyApplication.class
        -> Employee.class
        -> UserController.class
        -> OrderService.class

=> Which ClassLoader loads `MyApplication.class`?
    -> The Application ClassLoader loads `MyApplication.class`.
    -> Before loading, it follows Parent Delegation.
        -> Delegates the request to Platform ClassLoader.
        -> Platform delegates the request to Bootstrap ClassLoader.
        -> If Bootstrap and Platform cannot load the class, the request comes back.
        -> Finally, the Application ClassLoader loads the class.

=> What is Parent Delegation?
    -> Parent Delegation is the mechanism followed by Java Class Loaders.
    -> A child ClassLoader never loads a class immediately.
    -> It first delegates the request to its parent.
    -> The loading order is:
        -> Application ClassLoader
        -> Platform ClassLoader
        -> Bootstrap ClassLoader
    -> If the parent cannot load the class, the child loads it.

=> Why does Java use Parent Delegation?
    -> To avoid loading the same class multiple times.
    -> To improve security.
    -> To ensure that Core Java classes are always loaded by the Bootstrap ClassLoader.
    -> To maintain consistency throughout the JVM.

=> Why can't we override `java.lang.String`?
    -> Because of Parent Delegation.
    -> Bootstrap ClassLoader loads `java.lang.String` before the Application ClassLoader gets a chance.
    -> Even if we create our own `java.lang.String`, it will never be loaded.
    -> This prevents malicious replacement of Core Java classes.

=> What exactly is present inside a `.class` file?
    -> Bytecode instructions.
    -> Class metadata.
        -> Class name.
        -> Parent class.
        -> Implemented interfaces.
    -> Field information.
    -> Method information.
    -> Constant Pool.
    -> Access modifiers.
    -> Annotations (if any).

=> What is the difference between `.java` and `.class`?

    -> `.java`
        -> Human-readable source code.
        -> Written by developers.
        -> Can be edited.
        -> Compiled using `javac`.

    -> `.class`
        -> Compiled Bytecode.
        -> Generated by the Java Compiler.
        -> Executed by the JVM.
        -> Platform-independent.
        -> Cannot be directly understood by humans.

=> What are the phases of Class Loading?
    -> After a class is loaded into JVM memory, it goes through three major phases:
        -> Loading
            -> The Class Loader loads the `.class` file into JVM memory.
        -> Linking
            -> Verification
            -> Preparation
            -> Resolution
        -> Initialization
            -> Static variables are assigned their actual values.
            -> Static blocks are executed.
            -> The class becomes ready for use.

=> What happens during the Verification phase?
    -> Verification is the first step of the Linking phase.
    -> JVM verifies whether the Bytecode is valid and safe to execute.
    -> It checks:
        -> The Bytecode is not corrupted.
        -> The Bytecode follows JVM specifications.
        -> There are no illegal instructions.
        -> Memory access is valid.
        -> Type safety is maintained.
    -> If verification fails:
        -> JVM throws `VerifyError`.
    -> Purpose:
        -> Protect the JVM from executing invalid or malicious Bytecode.

=> What happens during the Preparation phase?
    -> Preparation is the second step of the Linking phase.
    -> JVM allocates memory for all static variables.
    -> Static variables are assigned their default values.
    -> No user-defined initialization happens here.
    -> Static blocks are NOT executed during this phase.

=> During Preparation, what values do static variables get?
    -> JVM assigns only the default values.

    Example:

    static int count = 100;
    static boolean status = true;
    static String name = "Vinay";

    During Preparation:

        -> count = 0
        -> status = false
        -> name = null

    -> The actual values (100, true, "Vinay") are assigned later during Initialization.

=> During Initialization, what happens?
    -> Initialization is the final phase of Class Loading.
    -> JVM assigns the actual values to static variables.
    -> JVM executes all static blocks.
    -> JVM executes them in the order they appear in the source code.
    -> After Initialization, the class is fully ready for execution.
    -> Finally, JVM invokes the `main()` method.

=> If both a static block and a static variable exist, which executes first?
    -> It depends on the order in which they are written in the source code.
    -> JVM executes static variable initializations and static blocks in source code order.

    Example 1:

    static int x = 10;

    static {
        System.out.println("Static Block");
    }

    Execution Order:
        -> x = 10
        -> Static Block

    Example 2:

    static {
        System.out.println("Static Block");
    }

    static int x = 10;

    Execution Order:
        -> Static Block
        -> x = 10

    -> Interview Tip:
        -> There is NO fixed rule that the static block always executes first.
        -> The execution always depends on the source code order.
